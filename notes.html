01 · Foundations

Why Terraform, in one slide

The console is fine for looking. It is terrible for remembering.

Click-ops

  • No record of who changed what, or why
  • Dev and prod drift apart within weeks
  • Rebuilding an environment is archaeology
  • Review happens after the change, if at all

Terraform

  • Desired state in Git — diffable, revertible, blame-able
  • One module, two environments, same shape
  • plan shows the blast radius before it happens
  • Review is a PR, like every other change we make
Declarative: you describe the end state. Terraform works out the create / update / destroy steps and the order.
  • Use a concrete example the team felt: a security group rule or subnet someone added by hand that nobody could explain later.
  • Stress "revertible" — reverting a PR is a real rollback path, and that's mostly what buys us calm during incidents.
  • Note the flip side honestly: once it's in Terraform, out-of-band console edits become drift and get stomped. That's the deal we're signing up for.
01 · Foundations

The core loop

Five commands cover about 95% of day-to-day work.

CommandWhat it doesWhen
terraform initDownloads providers, wires up the S3 backendFirst run, and after provider/module changes
terraform fmt -recursiveCanonical formattingBefore every commit — CI fails otherwise
terraform validateSyntax and type checking, no AWS callsFast local feedback
terraform plan -out=tfplanDiffs real infra against your codeEvery change. This is the review artifact
terraform apply tfplanExecutes exactly that saved planDev: you. Prod: the pipeline, after approval
# read a plan like a diff
  + create        ← new resource
  ~ update in-place ← safe-ish, read the attribute list
  -/+ replace     ← DESTROY then create. Stop and think.
  - destroy       ← why? on RDS or EKS this is an outage
  • The single habit to sell here: always plan -out, then apply that file. Applying a saved plan removes the "it changed between plan and apply" class of surprise.
  • Point at the -/+ line and say plainly: if you see replace next to RDS, the node group, or anything stateful, stop and get a second pair of eyes.
  • Mention plan output length — teach people to scroll to the summary line at the bottom first, then read upward for anything destructive.
02 · Our stack

What we're actually managing

Every service in our matrix falls into one of five layers. Layers apply in this order and are separated by state file.

1 Network

VPC, public/private subnets, Internet Gateway, NAT Gateway + Elastic IP, VPC endpoints (SSM, ECR, S3, Secrets Manager).

changes rarely · blast radius huge

2 Security

KMS keys, IAM roles with permission boundaries, OIDC provider + IRSA, Secrets Manager and SSM parameters.

gated writes in prod

3 Data

RDS PostgreSQL — the Recon database plus per-service databases, encrypted with our KMS key.

stateful · never auto-replace

4 Platform

EKS cluster and EC2 node groups, ECR repositories, internal ALB, ACM certificates, Route 53 records.

the busy layer

5 Observability

CloudWatch log groups, metrics, alarms. Cheap to change, easy to forget.

ship it with the service

Not in Terraform

App deployments and Kubernetes manifests. Terraform builds the cluster; our delivery tooling puts workloads on it.

  • Explain why layers are split: a typo in the platform layer should never be able to plan a destroy on the VPC or the database.
  • Smaller state per layer also means faster plans and fewer lock conflicts when two people work at once.
  • Layers talk to each other through remote state data sources or SSM parameters — outputs, not copy-pasted IDs.
  • Draw the boundary clearly at the end: Terraform stops at the cluster. Pods are someone else's pipeline.
03 · State

State is the whole ballgame

State is Terraform's map from your code to real AWS resource IDs. Lose it and Terraform will happily try to build everything a second time.

# envs/prod/backend.tf
terraform {
  backend "s3" {
    bucket         = "acme-tfstate-prod"
    key            = "platform/terraform.tfstate"   # one key per layer
    region         = "ap-south-1"
    dynamodb_table = "acme-tf-locks"              # stops concurrent applies
    encrypt        = true
    kms_key_id     = "alias/acme-tfstate"
  }
}

Rules

  • Versioning on for the state bucket — it is your undo button
  • One state key per layer, per environment
  • Let the DynamoDB lock do its job; if it's stuck, find who's applying

Never

  • Commit *.tfstate to Git
  • Hand-edit the state JSON
  • force-unlock without confirming nobody is mid-apply
  • Treat state as non-sensitive — it holds resource attributes in plain text
  • This is the most important slide. Slow down here.
  • The matrix already gives leads full S3/DynamoDB and engineers read-write — explain that this is deliberate, so nobody is blocked, but everybody is logged.
  • Tell the force-unlock story in the negative: an unlock during a live apply can leave half-created infrastructure with no record of it.
  • If someone asks about recovery: bucket versioning plus a prior version is the restore path, and it's a two-lead operation.
04 · Structure

Repo layout

Modules describe what a thing is. Environments describe how big and which account.

infra/
├── modules/
│   ├── network/      # vpc, subnets, nat, endpoints
│   ├── eks/          # cluster + node groups
│   ├── rds/
│   ├── ecr/
│   └── iam-irsa/
├── envs/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── backend.tf
│   │   ├── dev.tfvars
│   │   └── versions.tf
│   └── prod/
│       └── ... same shape
└── .github/workflows/terraform.yml

Why this shape

  • Same module, both envs. If it works in dev, prod differs only by inputs — not by code.
  • Separate directories, not workspaces. Different accounts, different state, no chance of applying to the wrong one because of a stale workspace select.
  • Pin everything. Terraform version, provider versions, module refs. An unpinned provider upgrade is an unplanned change.
  • Tag everything. Use provider default_tags so owner, env and cost-centre land on every resource for free.
  • Anticipate the workspaces question — someone always asks. Answer: workspaces share a backend and are easy to mis-select; separate directories make the blast radius visible in the file path.
  • Connect default_tags back to the billing line in the matrix: leads have Cost Explorer, but it only tells a useful story if tags are consistent.
  • Mention that a new environment should be a copy of envs/dev plus a different tfvars file — if it needs new module code, that's a smell.
04 · Structure

Modules and variables

A module with hardcoded values is a copy-paste waiting to happen.

# envs/prod/main.tf
module "eks" {
  source  = "../../modules/eks"
  env     = var.env            # "prod"
  vpc_id  = module.network.vpc_id
  subnets = module.network.private_subnet_ids
  node_instance_type = var.node_instance_type
  node_desired_size  = var.node_desired_size
}

# variables.tf — validate early, fail fast
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "prod"], var.env)
    error_message = "env must be dev or prod."
  }
}

Inputs

Typed, documented, validated. Defaults only where a default is genuinely safe.

Outputs

Expose IDs and endpoints. Other layers consume outputs, never hardcoded ARNs.

for_each over count

Keyed by name, so removing the middle item doesn't renumber and recreate its neighbours.

  • The for_each point is worth 20 seconds of real explanation — with count, deleting item 2 of 5 shifts indices and Terraform plans three unnecessary replacements. People hit this and panic.
  • Say that dev and prod tfvars should sit side by side in review, so a reviewer can see prod is bigger but not structurally different.
  • If asked about remote module registries: fine later, but pin to a version tag, never to a branch.
05 · Security

Secrets: what goes where

Terraform is bad at holding secrets, because anything it manages ends up in state.

Do

  • Create the secret container in Terraform; let the value be set out of band or generated
  • Read at deploy time via data sources, or from the pod via IRSA
  • Mark variables and outputs sensitive = true
  • Encrypt state, RDS, ECR, S3 and Secrets Manager with our KMS key
  • Rotate DB credentials on a schedule, not on a vibe

Don't

  • Put a password in a .tf or .tfvars file — it's in Git forever
  • Echo secrets in outputs or CI logs
  • Assume sensitive = true encrypts anything — it only hides it from console output
  • Bake static AWS keys into pods when IRSA exists
If a secret ever touches a plan, treat it as compromised and rotate it. Cheaper than the alternative.
  • Be blunt: state is plain-text JSON. Encryption at rest protects the file, not the person who can read the bucket.
  • Tie to the matrix — engineers have read-only on prod secrets precisely so a routine plan can't leak or overwrite production credentials.
  • IRSA is the headline security win: pod-scoped AWS access instead of node-wide keys, so a compromised pod gets one role, not the whole node's permissions.
05 · Security

Who can do what

Our permission matrix in one sentence: full freedom in dev, read and plan in prod, apply through the pipeline.

AreaDevProd
Compute, network, data
EKS, EC2, VPC, NAT, RDS		FullRead + plan
Secrets Manager / SSMLead full · engineer read-writeLead gated write · engineer read only
IAMCreate, within a permission boundaryLead authors · engineers no direct access
ECRPush / pullPull + promote — no rebuilding for prod
Terraform state (S3 / DynamoDB)FullRead-write to state and lock
Apply to prod—CI/CD pipeline role only
Break-glass—Audited, leads + one named engineer
  • Emphasise that "read + plan" on prod is not a demotion — everyone can still diagnose, diff and propose. What's removed is the ability to apply by accident.
  • The ECR rule matters: we promote the exact image tested in dev rather than rebuilding for prod, so the artifact is identical.
  • Permission boundaries on IAM stop a role from granting itself more than it should — worth one sentence.
  • Break-glass: explain it exists, it's audited, and using it means a written follow-up. Nobody should feel they need it for routine work.
06 · Pipeline

How a change reaches prod

Every prod change follows the same path. No exceptions, including for leads.

1 PR opened

fmt check, validate, tflint, and a security scan. Fast, fails loudly.

2 Plan on dev

Pipeline plans and applies to dev automatically. Reality check before anyone reviews.

3 Plan on prod

Read-only prod plan posted as a PR comment. This is what the reviewer actually approves.

4 Human approval

A lead approves the PR. For destructive plans, two.

5 Apply on merge

The gated apply role runs apply against the saved plan. OIDC, no long-lived keys.

6 Drift check

Nightly plan on both envs. A non-empty plan means someone clicked something.

  • The reviewer approves a plan, not just a diff of HCL. That distinction is the point of step 3.
  • The pipeline authenticates to AWS with OIDC and assumes a role — no stored AWS keys in CI.
  • Nightly drift detection is how we catch console changes early instead of discovering them mid-incident.
  • If asked "what if the pipeline is down and prod is on fire" — that's exactly what break-glass is for, and it's audited.
07 · Pitfalls

Things that bite

Every one of these has taken down someone's environment.

! Silent replace

A changed field on RDS or a node group can force -/+. Read the plan summary before approving.

! terraform destroy in the wrong directory

Guard stateful resources with prevent_destroy and keep RDS deletion protection on.

! Console fixes during an incident

Understandable, but write it back into code the same week or the next apply reverts it.

! Unpinned providers

A minor AWS provider bump can rewrite resource defaults. Commit the lock file.

! Routine -target

A debugging tool, not a workflow. It leaves state partially applied and hides drift.

! One giant state file

Slow plans, lock contention, and one blast radius for everything. Hence the layers.

  • Pick one or two of these to tell as a short story rather than reading all six — it lands better and saves time.
  • The console-fix point deserves nuance: we are not banning emergency action, we are requiring it be reconciled afterwards.
  • Mention that .terraform.lock.hcl belongs in Git — people delete it thinking it's noise.
08 · Reference

Commands worth knowing

Beyond the core loop — mostly for when something has gone sideways.

CommandUse it for
terraform state listWhat does Terraform think it manages?
terraform state show <addr>Inspect one resource's recorded attributes
terraform state mv <a> <b>Renaming or refactoring into a module without recreating
terraform import <addr> <id>Adopt something that already exists in AWS
terraform apply -replace=<addr>Deliberately recreate one resource (replaces old taint)
terraform output -jsonFeed endpoints and ARNs to other tooling
terraform force-unlock <id>Last resort, after confirming nobody is applying

State-mutating commands — mv, rm, import, force-unlock — are a lead-pairs operation in prod, never solo.

  • Frame the top three as everyday debugging tools, and the bottom four as "tell someone before you run this".
  • state mv is the one that saves refactors — without it, moving a resource into a module means destroy and recreate.
  • Note that import is how we'd bring any legacy hand-built resources under management if we find them.
09 · Checklist

The rules we hold each other to

If you remember nothing else, remember this list.

  • Plan before apply, always with -out
  • Read the plan summary — count the destroys
  • Nothing sensitive in Git, ever
  • Pin versions and commit the lock file
  • Small PRs — one layer, one intent
  • Dev first, prod never gets an untested module
  • Tag everything via default_tags
  • Prod applies go through the pipeline
  • Fix drift in code, not in the console
  • Ask before touching state
  • Slow right down and read these out — this is the slide people will screenshot.
  • Offer to paste this list into the team channel and pin it.
  • "Small PRs" is worth defending: a 400-line plan gets rubber-stamped, a 20-line plan gets reviewed.
Wrap up

Takeaways

1 Code, not clicks

If it isn't in the repo, it doesn't exist — and it will be reverted.

2 The plan is the review

We approve plans, not intentions.

3 State is precious

Remote, encrypted, versioned, locked, and never hand-edited.

Dev is where you experiment. Prod is where you replay something that already worked.
